### What the label really is

The competition is named *Pneumonia Detection*, but the target column encodes **lung opacity** — the radiographic
*sign*, cross-checked below against `stage_2_detailed_class_info.csv`:

| Target | Normal | No Lung Opacity / Not Normal | Lung Opacity |
|---|---|---|---|
| 0 | 8,851 | 11,821 | 0 |
| 1 | 0 | 0 | 6,012 images (9,555 boxes) |

Three decisions follow from that table and are stated rather than buried:

1. **Binary task, positive = `Lung Opacity`.** `Target == 1` maps exactly onto that class, so no rows are ambiguous.
2. **The negative class is heterogeneous.** 11,821 of the 20,672 negatives (57 %) are *abnormal for some other
   reason*, not a normal chest. The model is therefore learning "opacity vs everything else", not "sick vs well".
3. **Bounding boxes are not used for training.** This project is whole-image classification; the boxes are kept for
   the Grad-CAM comparison in Phase 3, where predicted heatmaps are checked against radiologist-drawn regions.

### Provenance, stated plainly

RSNA's own description says the images are *"frontal view chest radiographs from the 112,000-image public National
Institutes of Health (NIH) CXR8 dataset"*, and that *"Portable Network Graphics images were converted into Digital
Imaging and Communications in Medicine format, and patient sex, patient age, and projection were added to the DICOM
tags."*

**We verified that claim from the files rather than trusting it.** The evidence is in the absent-tag row above: a
scanner writes `Manufacturer`, `ImageType`, `PatientPosition` and a display window; a conversion tool writes none of
them. The pixels are 8-bit Secondary Capture — already display-encoded — not the 12–16-bit detector data a real
export carries. The `StudyInstanceUID` root is `1.2.276.0.7230010`, an OFFIS toolkit prefix, i.e. generated by
software.

So: **RSNA is a subset of NIH ChestX-ray14 whose PNG renders were wrapped in a freshly written DICOM envelope.**
They are genuine, valid `.dcm` files that Orthanc and `pydicom` accept, and they are not scanner-native. Both halves
of that sentence belong in the report. If scanner-native DICOM is required, the option on the brief's list is
LIDC-IDRI lung CT (Option 6, via the Cancer Imaging Archive — account required, much larger).

One direct consequence for preprocessing, found by executing the code rather than by reading: because
`WindowCenter` is empty, a Hounsfield-unit window applied to 8-bit data collapses the whole image into roughly grey
levels 64–79 — a near-uniform picture that a CNN cannot learn from. `src/data/dicom_io.py` therefore passes 8-bit
captures through untouched and windows only 16-bit data or an explicitly requested window.
`tests/test_dicom_io.py` pins this, and `results/plots/eda_windowing.png` shows the bug side by side with the fix.

Folds are asserted disjoint and complete. Split CSVs are written to `results/split_{train,val,test}.csv` and carry
`dicom_rel` (relative to the folder recorded as `path_base` in `results/eda_summary.json`) plus `PatientSex` and
`age` for the Phase 3 slice audit, so the same split trains in Colab without editing paths.

**The leak this dataset actually contains is row-level, not patient-level — and it is large.** Shuffling the
annotation rows of `stage_2_train_labels.csv` 70/30 puts **16.8 % of test rows on an image already present in
training** (1,524 of 9,069 rows; 1,499 images shared). Shuffling the one-row-per-image table gives 0. Measured in
§2 of the notebook.

**Be exact about what "patient-level" means here.** Every file carries its own unique `PatientID` — 26,684 files,
26,684 distinct PatientIDs, 0 files sharing one — because RSNA's de-identification broke the patient linkage when
they rebuilt the archive. So within-patient leakage *cannot occur in this release even in principle*. The grouping
code is written for archives where it does (LIDC-IDRI, MIMIC-CXR, any real clinical PACS, where one patient
contributes many films), and it is used here unchanged so that Phase 2 trains the same way it would on a real
deployment. Claiming "we prevented multi-film leakage" would be false; the honest claim is "we split on the image,
removed a measured 16.8 % duplicate-image leak, and the grouping abstraction prevents the multi-film variant that
this particular release happens not to contain."

### Preprocessing

- Windowing per `src/data/dicom_io.py`: real `WindowCenter`/`WindowWidth` when present; 8-bit captures passed
  through; otherwise 16-bit data windowed at the module defaults (1024 / 4096).
- Resize to 224×224; ImageNet mean/std normalisation.
- Augmentation on train only: horizontal flip, rotation ±10°, brightness jitter.
- No duplicate images: 0 fully duplicated annotation rows, and the image table is unique by `patient_id` (asserted).

### Known limitations of the data

- Derived from NIH ChestX-ray14; single-programme provenance, so limited device and population diversity.
- Pixels are 8-bit display-encoded renders, so the model never sees the original detector dynamic range.
- The negative class is 57 % "abnormal, but not opacity" — the model learns a sign, not a diagnosis.
- Boxes were drawn by 18 radiologists across 16 institutions, so label noise is real.
- **`PatientPosition` is absent on all 26,684 files, so the PA/AP view confound cannot be checked in this release.**
  The published PA/AP split (16,248 / 13,752) comes from RSNA's own documentation, not from anything measurable in
  the files we hold, and is therefore not used anywhere in this project.
- **5 images carry an impossible `PatientAge`** (max 155). They are kept as images — discarding a scan over a
  metadata typo is the worse error — but are excluded from age-band reporting and age is never a model input.
- `StudyDate` is the placeholder `19010101`, so no temporal drift can be measured within this dataset. The drift
  monitor in Phase 4 therefore compares *synthetic* distribution shifts against the train-split reference.

## Track B — Medical Segmentation Decathlon Task09 Spleen (Option 5)

| Field | Value |
|---|---|
| Name | MSD Task09_Spleen |
| Modality | Abdominal CT |
| Format | NIfTI (`.nii.gz`) |
| Cases | 41 training volumes |
| Size | ~2.3 GB |
| Access | Auto-downloaded by MONAI's dataset helper; no registration |
| Label | Binary foreground: spleen = 1 |

**Processing record** (`src/data/ct_volume.py` is the single source of truth for all four): volumes are
resampled to 1.5 mm isotropic spacing (originals are ~1.1–1.6 mm in-plane with 3–5 mm slices, so the slice
axis is what the resample mostly changes), windowed to [-150, 200] HU and scaled to [0, 1] with clipping,
and cropped 128³ per training patch. The split is 28 train / 7 val / 6 test volumes, seed 7, disjoint by
volume; the 6 test volumes are this project's own held-out set because Task09 has no public test labels,
so the test score is not comparable to published MSD leaderboard entries.

The per-case Dice table lives in `results/spleen_per_case.csv` (generated by notebook 05 on a Kaggle T4,
2026-10-27); summary in `docs/model_card.md` §Track B — mean 0.8586 over the 6 test volumes.

## Ethics statement

All data is de-identified at source and used under non-commercial terms. No patient data is committed to this
repository: the files under `data/` are git-ignored and held in DVC's cache, and only the `.dvc` pointer files —
which contain md5 digests and sizes, never pixels — are committed. The remote is Google Drive, reachable only after
registering a personal **Desktop app** OAuth client, because `dvc-gdrive`'s built-in shared client is refused the
`drive` scope by Google; the whole sequence is in `README.md`. The training machine still receives the images through
a plain Drive upload of the original archive rather than `dvc pull`, because Colab cannot run that interactive OAuth
flow. This separation is deliberate either way: a reviewer can
verify the exact bytes this project trained on from git alone, without being handed any image.

The images exist twice in DVC on purpose. The **folder** is the provenance record — 26,684 per-file md5s, which is
what lets a reviewer confirm the exact bytes behind every metric from git alone. The **archive** is the transport
record, because `dvc push` uploads one Drive object per cache file and 26,688 of them would take hours against
Drive's rate limits; the archive makes the push a single 3.5 GB resumable upload.

**What is actually in the remote.** The four single-file targets above are pushed to
`gdrive://1_MZ3txKpgRucQ5Ep8YxZAbKovIzDJFiL` and were checked back: Drive reports the archive object at
`files/md5/a8/307fbc6d9138a7760dafde21383714` with 3,534,067,864 bytes, i.e. exactly the size the pointer file
records, and the three CSVs at their own md5 paths with matching sizes (1,490,034 / 1,647,396 / 8,860,923 B).
`dvc status -c` says *Cache and remote 'gdrive' are in sync*. The image **folder** is not in the remote: its bytes are
already inside the archive, so pulling those 26,684 objects separately would buy nothing. A reviewer who wants the
pixels runs `dvc pull data/raw/rsna/stage_2_train_images.zip.dvc`; a reviewer who wants to verify the pixels match the
provenance record unzips it and compares against the folder revision. That folder id is public once this repo is — the
folder itself is private and holds no patient file that is not already inside the archive.

This system is for education only and is not a medical device.
